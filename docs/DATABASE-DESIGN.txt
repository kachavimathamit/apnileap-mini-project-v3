====================================================================
 MINI-PROJECT PORTFOLIO MONITORING PORTAL
 DATABASE DESIGN
====================================================================
Engine    : SQLite (better-sqlite3), WAL journal mode, foreign_keys=ON
Schema    : server/src/db/schema.sql
Migration : server/src/db/connection.js -> migrate()
              1. runs schema.sql (every statement is CREATE TABLE/INDEX/
                 TRIGGER IF NOT EXISTS, so it is safe to call on every
                 server start)
              2. addColumnIfMissing() adds any column that shipped after
                 a table already existed on disk - CREATE TABLE IF NOT
                 EXISTS cannot retrofit a column onto an existing table,
                 so this keeps older databases in step with schema.sql
                 without a destructive reset
Portability: no SQLite-only types are used beyond datetime()/julianday()
             helper functions, so the schema moves to PostgreSQL with
             near-mechanical changes if the deployment ever needs
             multi-node write concurrency.

Snapshot taken from the live database at time of writing:

  5 institutes, 9 departments, 3 projects, 11 users, 15 access grants
  235 audit log entries

--------------------------------------------------------------------
 DESIGN PRINCIPLES
--------------------------------------------------------------------

1. TENANT ISOLATION IS A COLUMN, NOT A CONVENTION
   Every institute-owned row - down to individual milestones, issues,
   KPI measurements - carries its own institute_id, even though it
   could technically be derived by joining through project_id. This
   is deliberate redundancy: it lets every scoped query filter
   directly on institute_id without a join, and it means a bug in one
   join path can never silently widen access to another institute's
   data. See docs/ARCHITECTURE.md section 4 for how this column is
   turned into an enforced SQL predicate on every request.

2. ROLES ARE GRANTED, NEVER ASSUMED
   access_grants is the single source of truth for "who can do what,
   where." A role by itself means nothing until it is paired with a
   scope (PLATFORM / INSTITUTE / DEPARTMENT / PROJECT) in a grant row.
   A CHECK constraint enforces that the scope columns actually match
   the declared scope_type, so a malformed grant cannot widen access
   by accident.

3. HISTORY TABLES ARE APPEND-ONLY AT THE DATABASE LAYER
   status_history and audit_log both carry BEFORE UPDATE / BEFORE
   DELETE triggers that abort the statement outright. This is
   enforced by SQLite itself, not by application code choosing not to
   call UPDATE - a bug, a bad migration, or a future developer cannot
   silently rewrite what happened.

4. DECIDED RECORDS BECOME IMMUTABLE
   progress_submissions follows the same idea one level down: once a
   submission is APPROVED or REJECTED it can no longer be edited or
   deleted (enforced by trigger). A student who disagrees files a new
   version; nobody edits history to make an old submission look
   different in hindsight.

5. SOFT DATA, HARD RULES
   Free-text fields (comments, rationale, descriptions) stay TEXT with
   no schema-level structure, because the requirements value the
   detail a reviewer or mentor actually writes over rigid
   categorisation. Everything that matters for a decision - RAG
   status, issue severity, review decision, escalation level - is a
   CHECK-constrained enum instead, so a workflow query never has to
   guard against a typo'd status value.

--------------------------------------------------------------------
 TRIGGERS (append-only enforcement)
--------------------------------------------------------------------

  status_history_no_update    BEFORE UPDATE ON status_history
  status_history_no_delete    BEFORE DELETE ON status_history
      Both RAISE(ABORT). The update trigger has one narrow carve-out:
      when a referenced user account is deleted, ON DELETE SET NULL
      needs to null out changed_by/approved_by, and SQLite implements
      that as an UPDATE. The WHEN clause lets exactly that one-directional
      nulling through and rejects every other kind of change.

  audit_log_no_update         BEFORE UPDATE ON audit_log
  audit_log_no_delete         BEFORE DELETE ON audit_log
      Same shape, same one narrow carve-out for actor_user_id.

  progress_submission_decided_immutable   BEFORE UPDATE
      Aborts if the row is already APPROVED/REJECTED and the update
      would keep it in that same decided state (i.e. blocks editing
      a decided row's content).

  progress_submission_decided_no_delete   BEFORE DELETE
      Aborts unless the row is still DRAFT.

9.0  WHY THIS SITS "AFTER GUIDE ALLOCATION"
--------------------------------------------------------------------
The handbook's framework is guide-owned at the team level and
faculty-owned at the theme level (Sec "Next Steps: Faculty Theme
Ownership", deck slide 95's "One Faculty -> One Theme"), and a formal
Gate review is run by a Reviewer against a specific team's
engineering evidence (Handbook "Roles & Expectations": Student /
Guide / Reviewer). Neither a theme assignment nor a gate schedule
means anything before a project has an accountable FACULTY_MENTOR -
exactly the same dependency the existing review_rubrics ->
scheduled_reviews mechanism already has on the guide relationship.

So, consistent with how rubric-driven reviews are already gated:
  - projects.theme_id may only be set by the API once the project has
    an APPROVED project_members row with member_role = FACULTY_MENTOR
    (i.e. after POST /assign-guide, mirroring the existing gate on
    /rubrics/:id/generate-reviews).
  - project_engines rows may only be created once a theme is set (an
    engine is a decomposition of the project's technical
    responsibilities, Handbook Sec 1.9) AND the project has an
    APPROVED FACULTY_MENTOR.
  - project_gate_reviews rows may only be created once at least one
    APPROVED, student-owned engine exists (Handbook Sec 1.9.1's
    validity test #8: "exactly one named owner accountable for its
    design decisions" - a gate cannot evidence work that has no owner
    of record).
  - project_weekly_checkins may be logged by the guide from the same
    point a guide exists, since the handbook positions weekly guide
    check-ins as continuous, distinct from the formal gate review.
This ordering is an application-layer rule (like the existing
definition-freeze gate), not a DB constraint SQLite can express
cleanly across role tables - document it here and enforce it in the
route layer exactly where /assign-guide already sits.

9.3  Gate model - gates / stage_definitions / stage_gate_map
--------------------------------------------------------------------
The handbook defines a fixed sequence of eight stages (S0-S7, Sec 1.7
Sequential Foundation + 1.8 Agile Technical Maturity Stages) reviewed
at five formal gates (Gate 0-4, Sec 1.12), for a fixed 50-mark split:
Gate 0 = 5, Gate 1 = 10, Gate 2 = 10, Gate 3 = 15, Gate 4 = 10. This is
genuinely platform-wide pedagogy, not per-institute policy - so, like
review_rubrics but unlike project data, it is modelled as a small
SEEDED REFERENCE catalog (global rows, institute_id-free) that a
PLATFORM_ADMIN can edit centrally rather than re-typing per
institute, and that seedFoundation.js UPSERTS on every server start
(not merely inserts-if-missing) - a corrected mark weight or stage
name in a future handbook revision must reach an already-running
deployment, which an insert-if-missing seed would never do.

A gate reviews a RANGE of stage maturity, not one single closing
stage: Gate 3 and Gate 4 both partially review S6/S7 (engine-level-
in-progress vs system-level-closed, per Table 1.12's "Maturity
evaluated" column). v1 modelled this as a single stage_definitions.
gate_id column with a closes_gate boolean, which cannot express that
overlap; v2 replaces it with a proper many-to-many join table.

------------------------------------------------------------- gates --
  id                     TEXT PK   "GATE_0".."GATE_4"
  sequence               INTEGER   0-4
  name                   TEXT   e.g. "Gate 0 - Problem Approval"
  marks_weight           INTEGER   5 / 10 / 10 / 15 / 10 (sums to 50)
  stage_range            TEXT   human-readable maturity range, e.g.
                              "S6 (system-level), S7" for Gate 4
  primary_review_focus   TEXT   the Table 1.12 "Primary review focus"
                              text for this gate
  course_outcomes        TEXT   JSON array of CO codes assessed at
                              this gate, e.g. ["CO4", "CO5"]
  default_week_number     INTEGER   nullable - the COE-calendar week
                              this gate is scheduled in by default
                              (Table 1.12); the actual date for a given
                              academic year lives in calendar_weeks

------------------------------------------------- stage_definitions --
  id                       TEXT PK   "S0".."S7"
  sequence                 INTEGER   0-7
  name                     TEXT   e.g. "Problem Definition and Need
                              Identification" (S0), "Root Cause
                              Analysis and Improvement" (S7)
  primary_question          TEXT   nullable - the stage's key question
                              (Table 1.4/1.7/1.8)
  expected_outcome          TEXT   nullable - the stage's typical/
                              expected outcome (same tables)
  description               TEXT   currently a copy of expected_outcome;
                              kept as its own column for a future
                              revision to diverge without a migration
  is_sequential_foundation   INTEGER   0/1 - S0 and S1 are common to
                              the whole team, "not sprinted and not
                              parallelised across engines" (Sec 1.7);
                              S2-S7 are Agile stages where engines may
                              sit at different maturity levels within
                              the same sprint (Sec 1.8)
  evidence_checklist         TEXT   JSON array, nullable. Fully
                              populated for S0 only (the Gate 0 Phase
                              Assessment Sheet's 8-item deliverables
                              checklist) - this handbook revision does
                              not yet document S1-S7 to the same
                              evidence-checklist level of detail, and
                              this column is left NULL for them rather
                              than inventing one. See 9.12 below.

  S0's evidence_checklist (verbatim from the Gate 0 Phase Assessment
  Sheet): Problem Discovery Note; Stakeholder Identification / Need
  Table; AS-IS Workflow / Current Process; Problem Statement; Scope &
  Out-of-Scope Statement; Technical & Operational Feasibility Note;
  Initial Risk & Constraint Register; Initial KPI / Success-Criteria
  Sheet.

------------------------------------------------------ stage_gate_map --
  stage_id   TEXT -> stage_definitions   CASCADE

  PRIMARY KEY (stage_id, gate_id)

  Seed rows (Table 1.12): S0->Gate0. S1->Gate1. S2,S3,S4->Gate2.
  S5,S6,S7->Gate3. S6,S7->Gate4 (again - the overlap this table exists
  to express).

9.4  sprints  (Handbook Sec 1.10-1.11: a Sprint is a shared execution
     window, a Stage is technical maturity, a Gate is a marked
     review - three different ideas, not synonyms)
--------------------------------------------------------------------
  id              TEXT PK   "SPRINT_1".."SPRINT_3"
  sequence        INTEGER   1-3
  name            TEXT   "Sprint 1" / "Sprint 2" / "Sprint 3"

  objective       TEXT   the sprint's recommended objective (Table 1.10)

9.6  gate_rubric_criteria  (the weighted assessment rubric behind each
     gate's marks - not a single opaque number)
--------------------------------------------------------------------
  id                 TEXT PK
  gate_id            TEXT -> gates   CASCADE
  sequence           INTEGER
  criterion_name     TEXT
  weight_marks       REAL   this criterion's share of the gate's total
  level_descriptors  TEXT   JSON object {"5": "...", "4": "...", ...,
                          "0": "..."}, nullable

  Gate 0's four criteria and their full 0-5 performance descriptors
  are transcribed verbatim from the handbook's own Gate 0 Assessment
  Rubric: Problem Discovery & Stakeholder Evidence (1.25); AS-IS
  Workflow, Problem Statement & Scope (1.25); Feasibility, Risks &
  Initial Success Criteria (1.25); Evidence Authenticity & Individual
  Understanding (1.25) - sum 5, matching "each criterion carries 1.25
  marks" in the handbook text (the handbook's own per-row "Weight: 5
  marks" label is a copy-paste artefact repeated identically on all
  four rows, contradicted by its own explicit formula sentence; the
  formula sentence is what is implemented).

  Gates 1-4 do not have their level descriptors published in this
  handbook revision, so their criteria are RECONSTRUCTED from Table
  1.3.1's CO -> stage -> gate -> marks breakdown, with level_
  descriptors left NULL:
    Gate 1 (10): SRS with FR/NFR (6); Traceability Matrix (2);
      Engine Decomposition and Ownership (2)  - directly stated in 1.3.1
    Gate 2 (10): System Architecture (4); Data Model and API Design
      (3); Algorithm and Business Logic Design (3)  - directly stated
    Gate 3 (15): Implementation and Version-Control Discipline (6);
      Engine Testing (6); RCA in Progress (3)
    Gate 4 (10): Final Working System (2); System Validation and
      Regression (3); RCA Closure (1); Report and Traceability (2);
      Individual Viva (2)
  The Gate 3/Gate 4 split is a reconstruction, not a direct quote:
  Table 1.3.1's own components for CO4 ("Implementation and version-
  control discipline (6) + final working system (2)") and CO5
  ("Engine testing (6) + RCA in progress (3) + system validation and
  regression (3) + RCA closure (1) + report and traceability (2)")
  are matched to whichever gate's Table-1.12 "primary review focus"
  each component phrase corresponds to (e.g. "RCA started" -> Gate 3's
  "RCA in Progress"; "defect closure" -> Gate 4's "RCA Closure"), and
  the match is only trusted because the resulting weights sum exactly
  to each gate's stated total (15 and 10) - including a 2-mark
  Individual Viva that Table 1.3.1 lists with no explicit mark value,
  inferred as the remainder needed to reach Gate 4's 10. Table 1.3.1's
  own "CO4: 25 marks" figure is NOT used directly - it does not match
  its own listed components (which sum to 8) and is almost certainly
  Gate 3 + Gate 4 combined (15 + 10 = 25), a merged-cell artefact from
  the source document's table. This entire reconstruction, and its
  verification logic, lives as a code comment directly above
  RUBRIC_CRITERIA_BY_GATE in server/src/db/seedFoundation.js.

9.10  V1 -> V2 MIGRATION (how an already-running database is corrected)
--------------------------------------------------------------------
connection.js's migrate() applies three different strategies depending
on what actually needs to change on a table that pre-dates v2:

  - gates, stage_definitions: ADDITIVE columns only
    (addColumnIfMissing), never dropped or rebuilt. A DROP TABLE gates
    was tried during development and rejected: project_gate_reviews.
    gate_id has ON DELETE CASCADE onto gates, so dropping gates
    cascade-deletes real gate-review rows, which hits their append-
    only trigger and aborts the whole migration. The old, now-unused
    `closing_stage_id` (gates) and `gate_id` (stage_definitions,
    still NOT NULL from v1) columns are left in place; seedFoundation.
    js detects whether stage_definitions.gate_id still exists and, if
    so, supplies a legacy value for it so the NOT NULL constraint on
    an old-shaped table is still satisfied.

  - project_engines: ADDITIVE columns only (the nine new template
    fields); `category`/`inputs_outputs` are left in place, unused.

  - project_gate_reviews: an actual REBUILD, because its CHECK
    constraint changed (4 decision values narrowed to 2) and two
    columns were removed (marks_awarded, bloom_answers, both moved to
    project_gate_review_scores) - changes SQLite cannot ALTER in
    place. migrate() renames the old-shaped table aside, lets
    schema.sql recreate it correctly, copies every row back with the
    old decision mapped onto the new enum (CONDITIONAL_PASS -> PASS;
    FAIL and RESUBMIT_REQUIRED -> RESUBMIT), and drops the renamed-
    aside copy. The old marks_awarded/bloom_answers values are not
    preserved in that copy, since per-student marks are now a
    genuinely different table this one no longer carries at all.

  - stage_gate_map, sprints, calendar_weeks, gate_rubric_criteria,
    project_gate_review_scores: brand new tables, created by CREATE
    TABLE IF NOT EXISTS with no migration concern.

  All of the above was verified against both a fresh database and a
  copy of the actual pre-v2 live database (including its one real
  demo gate-review row, which survives the rebuild correctly), and
  confirmed idempotent (migrate() run twice back-to-back produces no
  errors and no duplication).

9.11  What this deliberately does NOT change
--------------------------------------------------------------------
  - reviews / review_rubrics / scheduled_reviews are untouched. They
    remain the mentor-defined, per-team rubric-scoring mechanism
    already built (e.g. "Review 1/2/3"). project_gate_reviews is a
    parallel, separate mechanism for the handbook's fixed Gate 0-4
    academic-credit structure - the two are not the same concept (one
    is mentor-authored and flexible; the other is a fixed, 50-mark,
    programme-wide rubric) and should not be merged into one table.
  - RAG status (projects.rag_status) is left alone. A future
    enhancement could derive a RAG signal from gate outcomes (e.g. a
    Resubmit decision proposing RED), but that is a policy decision
    for the API layer, not a schema requirement, and is out of scope.

9.12  Known, documented gaps (not silently guessed answers)
--------------------------------------------------------------------
  - stage_definitions.evidence_checklist is populated for S0 only.
    Handbook v4 documents Week 1/S0/Gate 0 down to a faculty-execution
    and evidence-checklist level (its full Chapter 2); it does not yet
    document S1-S7 to the same depth. Rather than inventing plausible-
    sounding checklists for S1-S7, that column is left NULL for them.
  - gate_rubric_criteria.level_descriptors (the 0-5 performance
    descriptor text) exists only for Gate 0. Gates 1-4's criteria
    names and weights are a verified reconstruction (see 9.6); their
    prose descriptors are not published anywhere in the current
    handbook revision and are not guessed here.
  - project_themes.minimum_evidence and final_artefact_description
    are populated for 2 of the 10 themes only (the two the source
    material gives full worked-example detail for), NULL for the rest.
